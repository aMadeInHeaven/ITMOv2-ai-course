# Рефлексия по ДЗ 5: SDD, эмуляция двух команд и сравнение инструментов

## 1. Что делали
Мы реализовывали фичу «Избранные котики (Лайки) с фильтрацией» в проекте `cat-meme-site`.
Процесс был разделен на две независимые команды в разных чатах:
- **Команда UI (Чат 1):** проектировала кнопку-сердечко, переключатель «Только избранные», empty state и доступность.
- **Команда Логики (Чат 2):** проектировала модуль хранения ID в localStorage, синхронизацию и валидацию данных.

---

## 2. Что согласовали (Разбор конфликта спецификаций)
Когда обе команды выдали первые черновики спецификаций («до»), выяснилось, что они вообще не понимают друг друга:
1. **Разные имена методов:** UI ожидал вызовы `toggleLike(cardId)` и `isLiked(cardId)`, а логика назвала их `toggle(id)` и `has(id)`.
2. **Лишняя ответственность:** UI хотел, чтобы модуль логики управлял вообще всем каталогом карточек (`getCards`, `getVisibleCards`), тогда как логика сделала правильный изолированный стор чисто для ID избранного.
3. **Разный подход к событиям:** UI ждал метод `subscribe(callback)`, а логика реализовала нативное браузерное событие `window.addEventListener('favorites:changed')`.

Мы остановили процесс **до написания кода**, свели всё к единому общему контракту (`specs/02-shared-contract.md` и `specs/contract.yaml`), скорректировали обе спеки («после») и только потом сгенерировали код. В итоге интеграция прошла без единого конфликта, а `npm run check` сразу стал зеленым.

---

## 3. Сравнение инструментов: OpenSpec vs OpenAPI / Redocly

В ходе практики и домашки удалось сравнить два совершенно разных подхода к SDD:

### OpenSpec (впечатления от практики):
* **Как ощущается:** Очень удобный комбайн «всё в одном». 
* **Как работает:** Ты просто общаешься через слеш-команды (`/opsx-explore`, `/opsx-propose`, `/opsx-apply`, `/opsx-sync`). Под капотом OpenSpec сам собирает нужные системные промпты, подтягивает контекст проекта и следит за стадиями.
* **Плюсы:** Минимум рутины. Написал команду $\to$ агент сформировал спеку $\to$ проверил через CLI `openspec validate` $\to$ дал команду делать код. Весь флоу автоматизирован внутри чата.
* **Минусы:** Закрытость. Не всегда очевидно, что именно происходит под капотом этих команд, и такой процесс сложно масштабировать, когда две разные команды параллельно делают разные части одной фичи.

### OpenAPI + Redocly (впечатления от домашки):
* **Как ощущается:** Более ручной, строгий и контролируемый процесс.
* **Как работает:** Агенты не объединены общей CLI-утилитой. Приходится самому глазами вычитывать две независимые спеки, руками выявлять нестыковки и писать строгий файл контракта `contract.yaml`. Зато потом этот контракт прогоняется через жесткий линтер `npx @redocly/cli lint`, который на уровне типов и кодов ошибок (4XX) гарантирует правильность интерфейса.
* **Плюсы:** Полный контроль человека над архитектурой. Идеально для разделения фронтенда и бэкенда: пока контракт в YAML не утвержден и не проходит линтер, никто не пишет код.
* **Минусы:** Больше ручной работы. Приходится самому быть «мостом» между чатами, руками писать схему и следить за синхронизацией.

## 4. Чему научились
1. **Главная ценность SDD:** Найти нестыковку в названиях методов и форматах данных на этапе текстовой спеки занимает 2 минуты. Если бы мы сразу генерировали код — на отладку развалившегося UI и несовпадающих аргументов ушло бы полвечера.
2. **Роль человека:** Модели отлично генерируют код и документацию, но связать две независимые системы и принять архитектурное решение (где хранить состояние, как назвать API) может только человек.
3. **Инструменты бывают разными:** OpenSpec идеален для локальной фичи «в одни руки», а контрактный подход (OpenAPI/Redocly) незаменим при командной разработке и интеграциях.
