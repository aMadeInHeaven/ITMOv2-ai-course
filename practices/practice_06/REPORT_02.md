# Отчёт 2. Повторные атаки после исправлений

В данном отчёте зафиксированы защитные меры и результаты повторных атак после исправления уязвимостей в practices/practice_06/lab/service.py.

Реализованные защитные меры:
- SQL-инъекции (/profile, /search, /assistant/context):
  - Переход на параметризованные запросы (`?` + кортеж параметров).
  - Жёсткая валидация числовых параметров (`id`, `order_id`).
  - Для LIKE — параметризация шаблона `%q%` вместо подстановки строки.
- Авторизация staff (/admin/export):
  - Проверка роли через валидную серверную сессию (по `X-Token`), игнорирование заголовков от клиента.
- Манипуляция ценой (/orders):
  - Цена всегда берётся из серверного каталога `self.products[product]`; поле `price` из тела клиента игнорируется.
- Файлы и Path Traversal (/files):
  - Доступ только при валидной сессии.
  - Разрешено читать только файлы строго внутри `files/<username>` для текущего пользователя.
  - Проверка `allowed_root not in candidate.parents or not candidate.is_file()` плюс запрет на `private`.
- Инструменты AI (/assistant/execute):
  - Требуется валидная сессия.
  - Инструменты `export_profiles` и `delete_tree` доступны только для роли `staff`.
  - Для `read_file` применены те же ограничения пути, что и в `/files`.
- XSS (/reviews/view):
  - Экранирование пользовательского ввода: `html.escape(r['text'])`.
- Закрытие логов (/debug/logs):
  - Доступ к логам только у `staff` по валидному `X-Token`, иначе `403`.

Результаты повторных атак теми же пейлоадами:
- SQLi /profile: `GET /profile?id=1 OR 1=1` → теперь `400 Bad Request` (валидация `int()`).
- SQLi /search: `GET /search?q=%25'%20OR%201=1%20--%20` → `200 OK` и пустой список `[]` (параметризация LIKE).
- Подмена роли /admin/export: `GET /admin/export` c `X-Role: staff` без токена → `403 Forbidden`.
- Манипуляция ценой /orders: POST с `{price:1}` → `201 Created`, но цена равна каталогу (5000), манипуляция игнорируется.
- Path Traversal /files:
  - `?user=alice/../../private&path=operator-note.txt` → `403 Forbidden`.
  - Авторизованный alice: `?path=../bob/receipt.txt` → `403 Forbidden`.
- Инструменты AI /assistant/execute:
  - Без токена → `403 Forbidden`.
  - `export_profiles` без роли staff → `403 Forbidden`.
  - `delete_tree` без роли staff → `403 Forbidden`.
- XSS /reviews/view: вредоносный `<script>` теперь экранируется, исполняться не будет.
- /debug/logs: без роли staff → `403 Forbidden`.

Анализ AI-контура
- Почему критична бэкенд-валидация прав в /assistant/execute:
  LLM-подсистема не является источником истины о правах; модель — вероятностный инструмент, уязвимый к подсказкам пользователя и индиректным инъекциям через контент (отзывы, описания и т.д.). Если исполнять предложенные моделью действия без серверной проверки прав и аргументов, достаточно разместить вредоносный текст в отзыве, чтобы модель инициировала утечку или удаление данных. Поэтому серверная авторизация и валидация параметров обязательны.
- Почему недостаточно полагаться на системный промпт против indirect prompt injection:
  Системные инструкции могут быть переопределены или обойдены злоумышленником; LLM склонны следовать свежему пользовательскому контенту, а также уязвимы к техникам jailbreak/PII exfiltration. Единственный надёжный контроль — проверка прав на бэкенде и allowlist операций.
