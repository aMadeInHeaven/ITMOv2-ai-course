# План нагрузочного тестирования (RCTF)

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| 1) Happy-path POST /api/reviews с валидным diff (10KB) | 10 rps, 5 мин | P95 ≤ 500 ms; 2xx ≥ 99% | Латентность без участия LLM; стабильность ответа | app/api.py:35-38; app/api.py:40-42; app/review_service.py:19-22 |
| 2) Большой diff у границы (100KB) | 5 rps, 5 мин | Размер diff ≤ 100 KB (TO BE); P95 ≤ 500 ms | Влияние размера тела на задержку и ошибки | app/api.py:35-38; app/review_service.py:19-22 |
| 3) Пустой/отсутствующий payload["diff"] | 2 rps, 2 мин | 2xx ≥ 99% при валидных запросах; ошибки классифицированы | Поведение при отсутствующем ключе (без валидации) | app/api.py:35-38 |
| 4) Всплеск нагрузки (burst) | 50 rps, 60 сек | P95 ≤ 500 ms (без LLM); 2xx ≥ 99% | Устойчивость к коротким пикам | app/api.py:35-38; app/review_service.py:19-22 |
| 5) Последовательные запросы с различным diff | 5 rps, 10 мин | Деградация ≤ 10% p95 по сравнению с базой | Долгая сессия: дрейф lat/p95 | app/api.py:35-38 |
| 6) Таймаут LLM (симулируемый) | 3 rps, 5 мин | Время ожидания ≤ 1s (best practice); процент ошибок ≤ 1% | Риск: LLM.generate без таймаута | app/review_service.py:19-22 |

Примечания:
- Числа без источника помечены как best practice.
- Предел 100 KB помечен как TO BE, уточняется продуктово.

## Пороги отказа
1. P95 latency превышает 500 ms на 2 последовательных интервала — остановка теста, инициировать скейлинг API.
2. Доля 2xx падает ниже 99% более чем на 1 минуту — остановка, анализ ошибок, включить деградационный режим.
3. Размер тела diff > 100 KB (TO BE) — запросы отклонять/ограничивать, задать серверное ограничение.
