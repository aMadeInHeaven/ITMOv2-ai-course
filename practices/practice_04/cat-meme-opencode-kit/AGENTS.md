# Правила проекта «Котомемы»

## Контекст

Это статический лендинг без бэкенда. Базовый стек: Vite, HTML, CSS и vanilla JavaScript. Пользовательские карточки хранятся в `localStorage`. Не добавляй сервер, базу данных, авторизацию или новый UI-фреймворк без отдельного поручения.

Перед изменением кода прочитай:

- контракт: `docs/requirements.md`;
- правила интерфейса: `docs/style-guide.md`;
- skill: `.opencode/skills/cat-card-tdd/SKILL.md`;
- сценарии приёмки: `.opencode/skills/cat-card-tdd/references/acceptance-scenarios.md`.

## Фича A — список карточек с мемными котами

Нужно показать на главной странице адаптивный список минимум из шести стартовых карточек. Каждая карточка содержит изображение, заголовок и доступное текстовое описание изображения. Используй семантическую разметку списка и карточки; изображения не должны ломать сетку. Ошибка загрузки картинки должна превращаться в понятный плейсхолдер, а не в пустую область.

Критерии готовности:

- при первом открытии видны все стартовые карточки;
- карточки читаемы на ширине 320 px и на десктопе;
- у каждого изображения есть содержательный `alt`;
- карточки имеют стабильную структуру и одинаковые визуальные состояния;
- сценарий проверен тестом и Playwright MCP в работающем UI.

## Фича B — добавление новой карточки

Нужно дать пользователю форму с полями «Название», «URL картинки» и «Описание картинки». Валидная карточка добавляется в начало списка без перезагрузки и сохраняется в `localStorage`. После обновления страницы пользовательские карточки восстанавливаются. Невалидные данные не создают карточку: возле соответствующего поля показывается понятная ошибка, фокус переносится на первое ошибочное поле.

Ограничения безопасности и качества:

- разрешай только абсолютные URL с протоколом `http:` или `https:`;
- выводи пользовательский текст через `textContent`, не через `innerHTML`;
- не сохраняй невалидную карточку;
- не ломай сценарии фичи A;
- не очищай все данные сайта ради исправления одной записи.

Критерии готовности:

- валидная карточка сразу появляется первой;
- карточка остаётся после перезагрузки;
- пустые поля и опасный URL отклоняются доступным сообщением;
- повторная отправка не дублирует одну и ту же карточку;
- сценарий проверен тестом, runner и Playwright MCP.

## Порядок работы

1. Назови фичу и критерии, которые собираешься закрыть.
2. Добавь или измени тест так, чтобы он сначала падал по нужной причине.
3. Внеси минимальную реализацию и добейся прохождения проверки.
4. Запусти `node scripts/check.mjs`, затем `git diff --check`.
5. Для пользовательского сценария запусти приложение и проверь его через Playwright MCP.
6. Покажи diff, команды и результаты. Не делай commit без явной приёмки пользователя.

## Границы изменений

- Не меняй `docs/requirements.md`, `scripts/check.mjs`, тестовый runner, hook и настройки MCP ради зелёного результата без отдельного поручения.
- Не удаляй существующие тесты и не ослабляй утверждения.
- Не подменяй реальную проверку описанием того, что «должно работать».
- Для фичи B сохрани поведение фичи A.
